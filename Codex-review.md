## Frontend code quality

The project has a sound baseline in its FSD boundaries, typed props, focused UI primitives, and domain functions. The design principles below are useful review criteria. The largest issues are concentrated in components with several independent responsibilities and in styles that cross component boundaries.

### SOLID in this React codebase

| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Extract ownership of document sync and verb loading first. Move the existing Drill and Quiz components to separate files when touching that feature. ### KISS, DRY, YAGNI, and GRASP

- **KISS · Keep It Simple.** `PageHead` and `InlineConfirm` use ordinary React composition and native HTML. For the bulkier flows, simplify by giving one place ownership of a request or state transition. The progress store mutation in `App` during render is a concrete React and repository style violation. Move the mutation to document selection or an appropriate synchronization boundary. [App render](src/app/App.tsx#L235) · [Project React rules](CODE_STYLE.md#L52) · [React on render purity](https://react.dev/reference/rules/components-and-hooks-must-be-pure)
- **DRY · Share rules that must change together.** In-page tabs in Lesson, Lesson mode, and News duplicate tab markup and have different accessibility wiring. Share the keyboard behavior and the tab-to-panel relationship once that behavior is verified. Lesson history’s route-backed navigation has its own link and history contract. Likewise, share the heading and answer display across exercises where the behavior agrees. Keep typed and choice grading distinct because typed answers can receive accent feedback and choices require an exact match. [Lesson tabs](src/widgets/lesson-view/ui/LessonView.tsx#L234) · [Lesson mode tabs](src/pages/call/ui/LessonMode.tsx#L512) · [News tabs](src/pages/news/ui/News.tsx#L98) · [Exercise grading](src/features/make-exercise/ui/ExerciseRound.tsx#L47)
- **YAGNI and BDUF.** The code reviewed uses extensions for existing needs, as `RoundLoader` does for two exercise flows. A general-purpose exercise engine, theming framework, or extra repository layer would require evidence from current features before justifying its cost. Use one real slice to establish the pattern. BDUF means _Big Design Up Front_. It describes the development process, which this static snapshot alone cannot establish.
- **GRASP · Low Coupling.** Steiger enforces import direction. CSS still creates coupling between slices. Call-page selectors reach into the internal `.discuss-form` and `.book-import` classes. Give the embedded presentation an explicit owner so changing the inner markup stays local. [FSD rules](CODE_STYLE.md#L43) · [Embedded styles](src/app/styles.css#L3869)
- **GRASP · High Cohesion.** The separate Settings cards, `ExerciseHead`, and `InlineConfirm` have clear purposes. In `VerbsTab`, fetching, selection, and drill rendering change for different reasons. In `WordsTab`, group filtering and launching exercises deserve different boundaries when they next gain behavior. [Settings composition](src/pages/settings/ui/Settings.tsx#L19) · [ExerciseHead](src/shared/ui/ExerciseHead.tsx#L5) · [WordsTab state](src/widgets/word-list/ui/WordsTab.tsx#L132)
- **GRASP · Information Expert.** Homework matching belongs with the code that knows task identity, and `homeworkTasks` already delegates to the matching functions. Word and verb identity should likewise have one source in their respective domain models. Rows and caches should consume those keys consistently. [Homework model](src/widgets/lesson-view/model/homeworkTasks.ts#L9) · [Word progress keys](src/entities/word/model/progress.ts#L162) · [Verb state keys](src/features/conjugate-verb/ui/VerbsTab.tsx#L70)

### UI components and CSS ownership

Keep the existing small primitives. `InlineConfirm` makes Cancel the initial focus and handles Escape. `CallCard` connects its toggle to the content with `aria-controls` and preserves mounted state. These components share behavior as well as rendering. The biggest improvement would be to bring the lesson tabs to that standard, then untangle the stateful exercise screens as their bugs are fixed. [InlineConfirm](src/shared/ui/InlineConfirm.tsx#L18) · [CallCard](src/shared/ui/CallCard.tsx#L36)

`src/app/styles.css` is the sole first-party stylesheet, **4,591 lines** at review time, and the app entry imports it. Its theme variables, shared button styles, breakpoints, and reduced-motion rules are worth retaining. The cost is global ownership. One selector explicitly increases specificity to win over `.btn.ghost`, and the Call page restyles other features’ internals. The earlier build measured about **12 kB gzip** for the main stylesheet, so the immediate reason to move styles is maintainability. [Entry](src/app/main.tsx#L1) · [Theme](src/app/styles.css#L1) · [Button specificity](src/app/styles.css#L1817) · [Call overrides](src/app/styles.css#L3869)

Keep tokens, global defaults, shared primitives, and shell layout in global CSS. For a feature with clear ownership, move its private selectors alongside its UI in the same FSD slice. Use a CSS Module when names need to be local and verify behavior through the owning component, including any documented wrapper variants. The current code style specifies `src/app/styles.css`, so agree on the placement rule and update it when making the first move. A good pilot is Settings, with its page-local `.settings-*` rules. Compare both themes at phone and desktop widths, and check focus and reduced motion where relevant. [Settings styles](src/app/styles.css#L4302) · [Project CSS rules](CODE_STYLE.md#L99) · [Vite CSS Modules](https://vite.dev/guide/features.html#css-modules)

### Suggested order

1. **Small · Fix the in-page tab contract.** Start with the reported keyboard bug and cover navigation in a browser test before applying the shared behavior elsewhere.
2. **Medium · Separate sync and verb-loading ownership as their bugs are fixed.** Verify late responses, loading states, and language-aware keys at each boundary.
3. **Settings CSS pilot completed.** Settings owns its private selectors. The shared controls, theme, and shell remain global. Use the documented placement convention for later moves.
